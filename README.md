# 图像处理流水线 · 融合与分块执行引擎

把"每个算子整图读一遍写一遍"的图像处理流水线, 编译成"融合 + 分块"的执行
计划, 并自动选择调度方案。纯 Python + NumPy/SciPy 实现, 图像与流水线用仿真
代替, 验收时与逐个算子整图执行的结果逐像素核对。

```
imgpipe/
  dag.py         算子描述 (依赖半径 / 缩放 / 全局统计) + 窗口推导
  kernels.py     算子实现 (逐像素 / 邻域 / 缩放 / 直方图), 只处理矩形窗口
  pipelines.py   5 条仿真流水线 (电商缩略图、美化调色、两级缩放、纯逐像素、重去噪)
  imagegen.py    仿真图像 (多倍频程纹理 + 边缘 + 高光 + 传感器噪声)
  plan.py        流水线 -> 融合段 -> 组; 调度方案 Plan; 段内窗口推导
  runtime.py     执行引擎 (逐算子整图 / 融合 / 融合+分块)
  cost.py        代价模型 (标定的算子成本 + 带宽曲线 + 局部性修正)
  autotune.py    候选方案枚举 + 自动选择
  calibrate.py   微基准: 标定代价模型参数 -> calibration.json
  acceptance.py  验收: 逐像素核对 + 自动 vs 实测最优 + 内存/耗时测量
  report.py      跑完整矩阵, 生成 web/report.json
  memchild.py    子进程: 干净进程里量单方案峰值内存
  serve.py       本地静态服务器
tests/test_engine.py   正确性测试 (25 个)
web/index.html         可视化页面
```

## 快速开始

```bash
python3 -m pip install numpy scipy            # 依赖

# 正确性测试 (窗口推导、kernel 一致性、三种执行方式逐像素相同)
python3 -m pytest tests/ -q

# 标定代价模型 (可选; 仓库里带了 Apple M4 的 calibration.json)
python3 -m imgpipe.calibrate

# 跑验收矩阵, 生成报告 + 页面数据
python3 -m imgpipe.report            # 5 条流水线 x 4 个尺寸
python3 -m imgpipe.report --quick    # 小矩阵冒烟

# 看页面
python3 -m imgpipe.serve             # http://127.0.0.1:8000/
```

## 核心设计

### 1. 算子的依赖描述

一个算子只声明"输出的每个像素依赖输入的哪个矩形范围":

| 类型 | 描述 | 例 |
|---|---|---|
| 逐像素 `point` | 半径 (0,0) | 色彩矩阵、曝光、gamma、水印 |
| 邻域 `stencil` | 半径 (rx,ry) | 3×3 中值去噪、5×5 高斯、3×3 锐化 |
| 缩放 `scale` | 因子 (fx,fy) | 双线性缩放 |
| 统计 `stat` | 需要整图 | 直方图 (融合断点) |

窗口推导 (`WindowEstimator`) 和实际执行共用同一份取整/裁剪规则, 所以"推导出的
窗口"一定覆盖"执行时真正读取的像素"。缩放采样坐标定义在**全局网格**上, 只依赖
`(j+0.5)/f-0.5`, 与分块方式无关。

### 2. 算子融合

`build_segments` 按整图统计断点把流水线切成段; 段内把**相邻的逐像素算子合并
成一组**, 一组用两块 tile 缓冲 ping-pong 一次算完, 中间结果不落内存。邻域算子
和缩放各自成组, 需要上游按需多算一圈 halo (见下)。

### 3. 分块调度与按需重算

一个融合段按块调度时, 每块独立走完整段。**从输出块倒推每一级的输入窗口**
(`stage_windows`): 算子 k 的输出窗口 `w_out[k]` 由下游 `w_out[k+1]` 外扩 k+1
的半径得到, 这块多出来的边缘就是"按需重算的 halo"。

关键保证: kernel 在"恰好覆盖依赖范围"的窗口上算, 与在整图上算**逐位相同** ——
窗口内部的像素是真实邻居, 只有贴画布边缘时才 `edge` 复制, 而且复制出来的值只会
落在随后被裁掉的 halo 里。所以分块不改变结果, 只改变中间缓冲大小。

块尺寸的权衡:
* 块越大: 重算 halo 占比越低 (重算比例 → 0), 但工作集越大, 缓存命中越差;
* 块越小: 工作集能待在 L2/L3 里, 但重算 + 调用开销上升。

### 4. 整图统计断点

`stat` 算子 (直方图) 是强制断点。执行时先在断点输入上跑一遍收集直方图
(分块累加, 与顺序无关), 生成 LUT; 断点之后的段用这个 LUT 做均衡。前后两段
各自融合、各自分块。

### 5. 自动选择调度

`autotune.candidate_plans` 枚举候选 (融合开关 × 长条/方块/竖条多种块尺寸),
`cost.estimate_plan` 用代价模型排序, 选估算耗时最低的。代价模型 = 标定的
算子 ns/像素 + 分段带宽曲线 + 调用开销 + **局部性修正** (整宽条带的访存是
连续的, 实测比模型快 ~13%; 方块/竖条慢 ~5%) + **全局缩放** (标定成本是在
合成 tile 上测的, 实际流水线共享缓存/分配器, 综合比模型快 ~20%)。系数由
`calibrate.py` 标定, 全量实测回归后写进 `calibration.json` 的 `model_scale`。

## 验收结果

`python3 -m imgpipe.report` 在 5 条流水线 × 4 个尺寸上:

* **逐像素核对**: 融合、融合+分块的结果与逐算子整图基线**逐位相同** (最大误差 0)。
* **自动选择 vs 实测最优**: 中位差距 **2.4%** (p90 16%, 最大 23%), 即自动方案几乎
  总是选中或紧贴实测最优, 而它只是一次毫秒级静态估算 —— 不用把候选池真跑一遍。
* **加速**: 相对逐算子整图 (保留全部中间图), 中位 1.09×; 1280x960 及以上
  1.10–1.17×。收益随流水线变化: 含缩放/邻域的链收益最大, color_grade 只有
  ~1.1× (直方图断点把流水线切成两段, 每段本来就不长)。640x480 整幅都能进 L2,
  分块没有收益 (中位 0.96×), 代价模型会倾向选整图融合。
* **峰值内存**: 分块后单块工作集替代了整图中间结果, 峰值降到未融合的 **51%**
  (例如 photo_thumb 在 3000x2000 下 1138MB → 334MB)。"只融合不分块"几乎
  不降内存 (86%) —— 它仍然按整幅画布做融合段的中间缓冲, 降内存靠的是分块。

具体数字以页面为准 (由本机实测生成; 共享机器上绝对耗时会波动, 看相对关系)。

## 测量口径

* **耗时**: 进程 CPU 时间 (user+sys) 的最小值。共享机器上墙钟会被邻居干扰,
  CPU 时间稳定, 且它就是"这张图花了多少 CPU"。
* **峰值内存**: 每个方案在**独立干净进程**里跑一次, 取 `ru_maxrss` 超过输入图
  的部分。不能在同一进程顺序测 (分配器复用高水位, 后测的永远是 0), 也不能用
  fork (子进程继承父进程高水位)。
* **重算像素比例**: 执行器精确计数: 实际计算输出像素 / 唯一像素 − 1。

## 页面

`web/index.html` 读 `web/report.json`, 展示:
* 流水线的算子图与融合分组 (段的边界、统计断点);
* 一张图的分块方式 (块与块之间多算的 halo);
* 各方案的耗时、峰值内存、重算比例对比;
* 自动选择 vs 实测最优的差距。

## 依赖

NumPy 2.x, SciPy 1.x, pytest (测试)。页面无外部依赖, 纯静态。
